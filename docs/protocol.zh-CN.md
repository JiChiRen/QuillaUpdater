# QBOOT 串口升级协议

**中文** · [English](protocol.md)

QBOOT 引导程序在 UART 上使用的线上协议，以及本工具实际实现的那部分子集。
本文所有内容均取自固件源码，而非现有文档：

| 主题 | 固件中的权威来源 |
|---|---|
| 帧格式、命令分发 | `os/services/quilla-qboot/quilla-qiap.c` |
| CRC 算法 | `os/lib/crc16.c`（`crc16_add` / `crc16_data`） |
| 分区布局、页大小、解锁密钥 | `os/services/quilla-qboot/quilla-qboot-hal.h` |
| 签名校验、安全版本读取 | `os/services/quilla-qboot/quilla-qboot-secure.c` |
| `.quilla_secver` 布局 | `os/sys/quilla-app-secver.h`、`os/sys/quilla-version.h` |

两者若出现分歧，以固件为准。

---

## 1. 帧格式

收发两个方向完全一致。

```
+------+-----+----------+------------------+----------+
| SOF  | CMD | LEN (LE) | PAYLOAD          | CRC16 LE |
| 1 B  | 1 B | 2 B      | LEN bytes        | 2 B      |
+------+-----+----------+------------------+----------+
  0xA5
```

* `CRC16` 覆盖 `CMD | LEN | PAYLOAD`，**不含** `SOF` 字节。
* 算法：多项式 `0x1021`，反射，累加器初值 `0`。这是对 `crc16_add()` 的逐字节复刻，
  不是查表式 CRC。
* 累加式 CRC 可级联：`crc16(b, crc16(a)) == crc16(a + b)`。设备依赖这一性质，把每个
  DATA 负载折叠进一个持续累加的总和中。

SOF 位置上任何非 `0xA5` 的字节都会被丢弃 —— 主机正是靠这一点，忽略同一条线上设备输出的
文本 banner（`[BOOT] Quilla V...`）与 shell 回显。

## 2. 命令

| CMD | 名称 | 负载（主机 → 设备） | ACK | ACK 负载 |
|---|---|---|---|---|
| `0x01` | ENTER | `app_start` u32 LE + `unlock_key` 8 B | `0x81` | `status` u8 |
| `0x02` | DATA | `start` u32 + `end` u32 + `data` ≤ 256 B | `0x82` | `start` u32（回显） |
| `0x03` | END | `total_len` u32 + `total_crc16` u16 | `0x83` | `status` u8 |
| `0x04` | SIGN | `signature` 64 B（Ed25519） | `0x84` | `status` u8 |

`status == 0` 表示成功。

拒绝响应使用 `CMD = 0xC0 | phase`：

| NAK | 阶段 | 含义 |
|---|---|---|
| `0xC1` | ENTER | ENTER 阶段被拒绝 |
| `0xC2` | DATA | DATA 阶段被拒绝 |
| `0xC3` | 其他 | 帧级错误（通常是 CRC） |
| `0xC4` | SIGN | SIGN 阶段被拒绝 |

负载为单个原因字节：

| 原因 | 标记 | 成因 |
|---|---|---|
| `0x01` | ADDR | 地址超出 APP 区 |
| `0x02` | KEY | 解锁密钥不匹配 |
| `0x03` | CRC | 帧或字段 CRC 错误 |
| `0x04` | ERASE | Flash 页擦除失败 |
| `0x05` | PROG | Flash 编程或回读失败 |
| `0x06` | LEN | 总长度或总 CRC 不匹配 |
| `0x07` | SZ | 长度字段与实际数据长度不符 |
| `0x08` | SIGN | 签名未通过（未签名或密钥不匹配） |
| `0x09` | VER | 镜像中没有可用的安全版本区 |
| `0x0A` | ROLLBACK | 镜像版本低于设备的下限 |

**只有原因 `0x03` 值得重传。** 其余都是参数、密钥或 Flash 故障；重发同一帧只会浪费一次
40 秒的传输并掩盖真实成因，因此本工具立即中止。

## 3. 会话流程

```
主机                                      设备
 |                                        |
 |  （若处于 shell：文本命令 "qiap"）        |
 |--------------------------------------->|
 |                                        |
 |  ENTER(app_start, unlock_key)          |
 |--------------------------------------->|  校验 app_start 是否落在 APP 区，
 |<--------------------------------- 0x81 |  置 QIAP 标志
 |                                        |
 |  DATA(start, end, chunk)               |  新一页的首字节到达时擦除该页，
 |--------------------------------------->|  编程，并回显 start
 |<--------------------------------- 0x82 |
 |            ... 重复 ...                 |
 |                                        |
 |  END(total_len, total_crc)             |
 |--------------------------------------->|  校验级联 CRC 与总长度
 |<--------------------------------- 0x83 |  提交并复位（无公钥）
 |                                        |  仅返回 ACK（已烧录公钥）
 |  SIGN(signature)                       |
 |--------------------------------------->|  SHA-256 + Ed25519，片内完成
 |<--------------------------------- 0x84 |  提交，写 APP 标志，复位
 |                                        |
 |  === 完成结论，三种构建都在此 ===       |  复位之前
 |  ... 设备重启 ...                       |
 |<------ "[QAPP] <name> V<ver>" ---------|  可选的后置确认
```

`END` 的行为取决于 QBOOT 构建变体：

* **QBOOT_CHECK**（CHECK 模式，无公钥）：`END` 直接提交并复位，`SIGN` 根本不会被发送。
* **QBOOT_SEALED / QBOOT_SEC**（SEALED / SECURE 模式，有公钥）：`END` 仅返回 ACK；APP
  标志的写入与 MCU 复位都要等到 `SIGN` 校验通过之后。跳过 `SIGN` 会使本次升级停留在
  未提交状态。

两条路径都是 `commit_app()` 在前、完成 ACK 在后，因此三种构建的完成依据都能在**复位之前**
取得。启动戳为何不作为判据，见 7.3 节。

主机无法仅凭协议判断当前属于哪种情况 —— 协议没有能力查询 —— 因此改为探测设备行为：
收到 `ACK 0x83` 后，短暂监听 `[QIAP] flash complete. Rebooting into APP...`（旧版 QBOOT
打印 `[QIAP] success. Rebooting...`）。该公告只在 `done=1` 之后、提交复位之前输出。
监听到，说明设备已自行提交，跳过 `SIGN`；未监听到，说明设备是等待签名的带公钥构建。

向一台已提交的设备发送 `SIGN` 不只是多余：APP 的 shell 不讲 QIAP，不可能产生 `ACK 0x84`，
主机将在一块已经在运行新固件的板卡上白等满 `SIGN_TIMEOUT`。

## 4. 进入升级模式

设备可能处于以下四种状态之一。操作者不应被要求知道是哪种，因此由主机探测：

| 状态 | 指纹（`part` 回复） | 主机动作 |
|---|---|---|
| A. 升级空闲态，残留 QIAP 标志 | banner 含 `enter upgrade mode` | 直接发送 ENTER |
| B. QBOOT shell | 回显含 `qboot` | 发送 `qiap`，等待 `enter upgrade mode`，再发 ENTER |
| C. APP shell（固件运行中） | 回显含 `app1` | 发送 `swqboot`，等待 `[BOOT]`，转入 B |
| D. 升级空闲态，原始接收 | 回复为空，无回显 | 直接发送 ENTER |

「发一个换行、找一个 `>` 提示符」这种探测无法区分 B 与 D：shell 不会因为空行而重印提示符，
两者都返回空。真正的判别依据是 `part` 的回显；而在状态 D 下，尽管文本命令会被吞掉，
二进制 ENTER 帧仍然能到达状态机。

## 5. 签名对象

`SIGN` 携带的 64 字节 Ed25519 签名，签署内容是：

```
image_len (u32 LE) || SHA-256(image)
```

与 `quilla_qboot_secure_verify_descriptor()` 一致。

安全版本**不在**签名对象内。QBOOT 直接从镜像自身读取，位置为 `APP_START + 0x400`：

```c
struct {
    uint32_t magic;    /* 0x31564151，即小端的 "QAV1" */
    uint32_t version;  /* QUILLA_APP_SECURITY_VERSION */
} quilla_app_secver_t;
```

当 `version` 低于其防回滚下限时拒绝该镜像（`NAK 0x0A`）。主机既无法提供也无法降低该版本号：
它作为普通镜像内容被签名覆盖，比较在设备侧完成。

长时间传输之前先交叉核对：本工具从 `.bin` 中读出同样的 8 个字节并在界面上显示版本号，
使降级问题在写入 40 秒之前就被发现，而不是之后。

## 6. 分区布局

物理顺序为 BOOT → META → APP。

| 区域 | 地址 | 大小 | 说明 |
|---|---|---|---|
| QBOOT | `0x08000000` | 24 KiB | 正常运行时只读 |
| META | `0x08006000` | 4 KiB | 磨损均衡双槽：标志、下限、封印、清单 |
| APP | `0x08007000` → `SOC_FLASH_END` | 取决于 MCU | 升级目标 |

`APP_START` 由 META 布局固定，在所有当前 MCU 上一致。`APP_END` 取决于 `SOC_FLASH_END`
（PY32F040xB = 128 KiB → `0x0801FFFF`，GD32F502VE = 512 KiB），因此主机**从不**写死它：
而是通过 `pinfo` shell 命令向设备查询，并把回复作为写入前的上限。若 `pinfo` 不可用
（旧固件，或已处于原始接收态），主机跳过自身检查，改由设备的 `ADDR` NAK（`0x01`）执行真实边界。

擦除粒度为 1 页（256 B），因此只有页对齐是有意义的约束。

## 7. 时序约束

这些是固件的属性，不是可调参数。改动它们会破坏链路。

### 7.1 接收链路：QBOOT 的环形缓冲，而非 APP 的 shell 端口

升级全程在 QBOOT 内完成，因此尺寸约束来自 QBOOT 的接收链路，而不是 APP 的 shell 端口：

| 环节 | 大小 | 行为 |
|---|---|---|
| USART2 RX DMA | 1024 B，CIRCULAR | 永不重装；主循环阻塞在 Flash 页擦除期间仍在持续接收 |
| QBOOT 桥接环 | 512 B | `qboot_rx_sink()` 溢出即丢弃；容量按容纳一整帧 270 B 设计 |
| QIAP 负载缓冲 | `PAGE_SIZE + 8` = 264 B | `QUILLA_QIAP_MAX_PAYLOAD` |

`CHUNK = 256` → DATA 帧负载 `8 + 256 = 264` B，线上 `270` B；SIGN 帧 `6 + 64 = 70` B。
旧文档中的「64 字节 NORMAL（乒乓）DMA」限制，描述的是后来已被 CIRCULAR DMA 取代的固件版本。

桥接环是字节流缓冲而非帧缓冲，但容量按容纳一整帧设计（512 B 对 270 B 的帧），
因此一帧会原子地进入，不会被拆到两轮之间。QBOOT 每轮都会把它弹空，占用量取决于两轮
之间的积压（一次主机写入突发），而非帧长。真正会压垮它的是流水线式连发帧，而非帧太长。

真正保证环形缓冲安全的是**停止等待握手**：同时只有一帧在途，收到 ACK 才发下一帧。页擦除
期间线上没有任何字节，因此桥接环永远不会收到超过一帧的突发，也就永远不会溢出。这也是
1024 字节的 DMA 环足以覆盖约 460 字节擦除窗口的原因。

主机必须遵守的推论：

* 始终保持恰好一帧在途。会造成桥接环溢出的是流水线式发帧，而不是帧长。
* `CHUNK = 256` 是硬上限：`QUILLA_QIAP_MAX_PAYLOAD` 等于 `PAGE_SIZE + 8`，设备会把任何
  LEN 超过该值的帧直接丢回 SOF。256 同时使一帧恰好等于一页，这正是写入变为「每页一次擦除」
  而非「每六帧一次擦除」的原因。
* DATA 帧回显了**不同**的起始地址，意味着整帧丢失；重发无法自愈，因此会话被报告为失步，
  必须由操作者复位板卡。

在 115200 链路上，一帧 270 字节（23 ms）加一次 ACK 往返（约 2 ms）再加一次约 30–40 ms 的
页擦除，实际上限约为 4–4.5 KiB/s：128 KiB 镜像约需 30–35 秒，而 `CHUNK = 48` 时为 40–60 秒。

### 7.2 SIGN 需要长超时

收到 `SIGN` 后，设备会在片内完成一次完整校验：

| 步骤 | 耗时 @ 8 MHz（PY32F040） |
|---|---|
| 对镜像做 SHA-256 | 约 0.56 s |
| Ed25519 校验 | 约 20.11 s |
| **合计** | **约 20.6 s** |

上述数字是按指令条数估算的通用实现耗时。参考 PY32F040xB 板卡运行当前 QBOOT 时，`SIGN` 帧
发出后约 3 秒即回 `ACK 0x84`，因此该表应视为上界，而非实测值。

* `SIGN` 的 ACK 超时必须覆盖最坏情况；本工具取 90 秒且不下调，因为判断错误的代价是在一块
  已经正确烧录的板卡上误报失败。
* `SIGN` 只发送**一次**。重传会让设备验签两次并使状态机错位。
* 界面必须如实说明，否则操作者会在一次健康的升级过程中拔掉线缆。界面点名该阶段，但不承诺
  固定时长。

### 7.3 完成结论与启动戳

升级在**复位之前**就依据 QBOOT 侧的证据宣布完成：

| 构建 | 模式 | 完成证据 |
|---|---|---|
| QBOOT_CHECK | CHECK（无公钥） | `ACK 0x83` + `[QIAP] flash complete...` |
| QBOOT_SEALED | SEALED（有公钥） | `SIGN` 之后的 `ACK 0x84` |
| QBOOT_SEC | SECURE（有公钥） | `SIGN` 之后的 `ACK 0x84` |

完成 ACK 丢失时，可由提交公告或匹配的 `[QAPP]` 启动戳兜底；复位导致的端口掉线记为
**弱证据**并明确写进日志，因为拔线与复位无法区分。若端口仍然活着且没有任何证据，则
判定失败。

复位之后，设备先跑启动检查再进入 APP：

| 模式 | 启动开销 |
|---|---|
| CHECK | SHA-256 完整性校验，约 0.1 s |
| SEALED（默认） | SHA-256 + 封印比对，约 0.6 s |
| SECURE | 完整 Ed25519 校验，数秒至数十秒 |

三者相差两个数量级，因此主机**不等待**其中任何一种：只对随完成码一同到达的字节做
0.5 秒的检查，若含 `[QAPP]` 则与 `FirmwareImage.expected_stamp` 比对后记录，否则忽略。
`wait_app_stamp()`（45 秒）保留给显式想观察新固件启动的调用方，不参与 `run()` 的结论。

## 8. 本工具不做的事

* 不解析 `.hex` —— 升级路径只接受原始 `.bin`。
* 不做 A/B 槽管理，也不做镜像暂存：`ENTER` 即开始对 APP 区就地写入。
* 不做密钥烧录。公钥在构建时通过 `-DQUILLA_SECURE_BOOT_PUBKEY={...}` 编译进 QBOOT；
  本工具只负责用私钥签名。

## 9. 掉电行为

一旦 `ENTER` 被接受，QIAP 标志即置位，因此在提交之前掉电，设备下次启动会停留在升级空闲态
（上文状态 A），而不会跳进一个写了一半的镜像。重新运行工具即可恢复。

**未受保护**的窗口：在 APP 标志写入之后、复位之前掉电（此时 `SIGN` 已校验通过）。这种情况下
QBOOT 的行为取决于该版本如何处理「已提交但未复位」的标志。该路径超出了本主机工具能观测的
范围，也未在此验证过 —— 若这一点对你的产品重要，请在目标板上实测，而不要依据本文。
